## 二、为什么这么断言

**① 结构用 schema，值用业务断言，两者不互相替代**

列表、商品、错误响应各写了一份 schema：
- `LIST_SCHEMA`：`additionalProperties: false` —— 故意从严，接口多返回字段时会红
- `PRODUCT_SCHEMA`：不限制额外字段 —— 商品字段多且易变，限制会过度脆弱
- `ERROR_SCHEMA`：只要求 `message` 非空字符串，因为错误体的业务含义无法用结构表达

**② 不只断状态码**

分页断"条数等于 limit 且回显的 limit 一致"；
排序断"全量价格序列与 sorted() 结果相等"——如果只断 200，接口把排序忽略掉我也发现不了；
`select` 断"键集合恰好等于 {id,title,price}"，而不是"包含"。

**③ 为什么用参数化**

`limit` 两类非法值、`order` 两种方向、商品 id 两种情况，逻辑完全相同、只有输入不同。
参数化让每个输入成为独立用例（独立结果、独立耗时），并在报告里显示为 `test_...[-5]`、`test_...[abc]`。

**④ 边界与负向的区分**

- `order=hhh` 是**负向**：参数值违反了接口约定 → 期望 400
- 搜索无结果是**边界**：请求本身合法，只是数据为空 → 期望 200 + 空数组，**不是 404**

这个区分很重要：很多接口把"查不到"错误地返回 404，等于把业务状态和错误混为一谈。

## 三、探测中发现的异常行为（重要）

| 请求 | 返回 | 判断 |
|---|---|---|
| `GET /products?limit=0` | **200，返回了全部 30 条** | ⚠️ 可疑：`limit=0` 通常应返回 0 条，这里被当成"不限"处理 |
| `GET /products?sortBy=nosuchfield` | **200，忽略排序** | ⚠️ 可疑：非法排序字段没有报错，静默忽略，调用方难以发现拼错 |
| `GET /products?select=xxxabc` | **200，每条只剩 `{"id": N}`** | 可接受但需注意：请求了不存在的字段，接口不报错而是返回最小字段集 |
| `GET /products/search?q=`（空关键词） | **200，返回全量** | 可接受：空关键词等价于不筛选 |
| `GET /products/abc` | **404，message 为 "Product with id 'abc' not found"** | 合理：非数字 id 也走同一套"不存在"语义 |
| 所有错误响应 | 统一结构 `{"message": "..."}` | ✅ 错误体有稳定契约，可直接写 schema |
| `POST /products/add` | **201**，且路径带 `/add` | 注意：REST 惯例是 `POST /products`，这里是 `/add` |
| `DELETE /products/1` | **200，返回被删对象** | 注意：不是 204 No Content，且是"假删除"（数据不会真删） |

**结论**：`limit=0` 与 `sortBy` 静默忽略这两条，我会作为缺陷候选提交给开发——
测试的价值不是让用例全绿，而是把这些"看起来正常但不合预期"的行为暴露出来。

## 五、404 的两种含义（契约区分）

### 5.1 实测现象

同一个状态码 404，`dummyjson` 会返回两种完全不同的响应：

| 请求 | 状态码 | Content-Type | 响应体（截断） |
|---|---|---|---|
| `GET /products/99999` | 404 | `application/json` | `{"message":"Product with id '99999' not found"}` |
| `GET /products/abc` | 404 | `application/json` | `{"message":"Product with id 'abc' not found"}` |
| `GET /productsx` | 404 | `text/html` | `<!DOCTYPE html> ... <title>Error</title>` |
| `PUT /products` | 404 | `text/html` | 同上（HTML 错误页） |

### 5.2 两类 404 的定义

**① 业务级 404（Business 404）**

- 触发条件：路由**已合法注册**，但请求的**资源在数据集中不存在**。
  例：`GET /products/99999`，`/products/{id}` 路由存在，只是没有 id=99999 这条数据。
- 表现：统一 JSON 错误体，`Content-Type: application/json`，含非空 `message`。
- 契约状态：符合预期。错误体结构稳定，可作为客户端解析依据。

**② 路由级 404（Route 404）**

- 触发条件：请求的 URL 路径在服务中**没有注册任何路由**，或方法未匹配。
  例：`GET /productsx`、`PUT /products`。
- 表现：由 Web 框架的**默认错误页**接管，返回 HTML，`Content-Type: text/html`。
- 契约状态：**不符合预期**。返回格式与业务错误体不一致，客户端按约定调用 `resp.json()` 会抛异常。

> 关于框架：该服务的实现框架未确认。但可以确定**不是 FastAPI**——
> FastAPI 的默认 404 返回 JSON `{"detail": "Not Found"}`，而不是 HTML 错误页。
> 本文档只记录可观测行为，不推断内部实现。
>
> 关于数据来源：该服务是公开演示环境，数据存放方式未确认（不假设为数据库），
> 本文统一表述为"数据集中不存在"。

### 5.3 测试断言策略

**关键认知：测试只能断言"外部可观测的现象"。**
"路由是否注册"是内部原因，无法从响应直接观测；可观测的判据是
**`Content-Type` + 响应体结构**。因此断言必须做三层，不能只看状态码：

| 层级 | 断言内容 | 作用 |
|---|---|---|
| ① | `status_code == expected_status` | 最基本契约 |
| ② | `Content-Type` 含期望的类型 | **区分两类 404 的关键** |
| ③ | JSON 响应体的结构（`message` 非空） | 业务错误的可用性 |

第 ② 层通过数据字段 `expected_content_type` 声明（默认 `application/json`），
使"同一个 404、两种格式"可以在同一张矩阵里被精确表达，而不是把
"所有响应都必须是 JSON"硬编码进测试函数。

### 5.4 用例映射与结果

| 用例 | 断言什么 | 结果 |
|---|---|---|
| `test_error_matrix[resource_not_exist]` | `/products/99999` → 404 + JSON | 通过 |
| `test_error_matrix[product_id_not_number]` | `/products/abc` → 404 + JSON | 通过 |
| `test_error_matrix[wrong_path]` | `/productsx` → 404 + **HTML**（现状快照） | 通过 |
| `test_business_404_returns_json` | 业务 404 必须是 JSON 且 message 可用 | 通过 |
| `test_route_404_returns_html_today` | 路由 404 当前返回 HTML（钉住现状） | 通过 |
| `test_error_matrix[wrong_http_method]` | `PUT /products` 期望 405，实际 404+HTML | **xfail**（已知缺陷） |
| `test_route_404_should_be_json` | 路由 404 按契约应返回 JSON | **xfail**（已知缺陷） |

同一位置保留一条"记录现状"（绿）和一条"记录期望"（xfail）：
前者防止行为被无意改变，后者在缺陷修复时会因 `XPASS(strict)` 转为失败，提醒撤销标记。

### 5.5 小结

> **判断依据不是"返回码是不是 404"，而是"响应格式是否符合错误体契约"。**
> 路由级 404 的 HTML 会直接打断客户端的 JSON 解析，属于需要跟踪的缺陷；
> 业务级 404 的 JSON 是正常契约，属于预期行为。

## 六、超时阈值怎么定

### 6.1 原则：基线采样 + 冗余系数

超时阈值不采用主观估计，按以下四步确定：

1. **选取代表性接口**：区分「快速失败类」（参数校验失败、资源不存在）与
   「数据查询类」（列表、详情、分页）、「写入类」。
   快速失败类不查数据，基线应显著低于查询类。
2. **控制环境**：无并发干扰，预热后再采样，排除冷启动与连接初始化抖动。
3. **连续采样 N 次（建议 20~50）**：取 **P95** 作为基线。
   不用平均值——平均值会被偶发尖刺拉低，掩盖尾部延迟。
4. **区分链路**：本机回环（127.0.0.1）与公网链路是两个量级的基线，必须分别采样。

### 6.2 计算公式

| 场景 | 冗余系数 | 理由 |
|---|---|---|
| 单元/接口自动化（本机 mock） | 2 ~ 3 | 环境稳定，只需防偶发卡顿；系数过大会掩盖性能退化 |
| 集成测试 / 预发布 | 3 ~ 5 | 共享资源存在波动 |
| 生产网关 / 前端请求 | 可再放大，但建议 ≤ 10 | 需叠加网络抖动与排队 |

### 6.3 本项目实测基线

采样日期 2026-11-01，采样方式为连续请求取 P95（脚本见 6.5）。

| 被测目标 | 链路 | 实测基线 | 波动情况 | 本项目采用的阈值 |
|---|---|---|---|---|
| `dummyjson.com`（公网） | 公网 HTTPS | P50 ≈ 1~2s，常见 2~6s | **偶发 30s 级超时（SSL 握手阶段）** | `timeout=10` + `retries=1` |
| 本地 mock（第 8 课 `server.py`） | 127.0.0.1 回环 | < 50ms | 稳定 | `timeout=5` + `retries=0` |

**关于"错误码矩阵该用短超时"的修正**：初版设想给错误码用例配
`timeout=5, retries=0`（4xx 应秒回）。实测在公网链路上不成立——
13 条矩阵用例中有 3 条 200 用例因 ReadTimeout 失败，而单独重跑全部通过，
说明是链路抖动而非逻辑问题。因此矩阵用例改为 `timeout=10, retries=1`。
**"极短超时 + 零重试"只适用于本地可预测的服务。**

### 6.4 两类超时的区别与落地现状

| | 请求级超时 | 用例级超时 |
|---|---|---|
| 控制对象 | 单次 HTTP 请求 | 整条用例的执行时长（含夹具、断言） |
| 实现方 | `requests`（`ApiClient.timeout`） | `pytest-timeout` 插件 |
| 超时表现 | 抛 `requests.exceptions.ReadTimeout` | 直接终止该用例 |
| 本项目状态 | **已生效**，默认 30s，可用环境变量 `TIMEOUT` 覆盖 | **未启用**：`pytest-timeout` 尚未安装 |

请求级超时的生效性已验证：注入 `TIMEOUT=2` 后请求慢接口，抛出
`ReadTimeout (read timeout=2.0)`，撤销后恢复 30.0。
（注意：`@pytest.mark.timeout()` 在未安装插件时是**无效标记**，只产生一条 warning，
不会真正限制耗时——写之前必须先装插件并登记到 `requirements.txt`。）

### 6.5 基线采样脚本

```python
import statistics
import time

import requests


def sample(url: str, n: int = 20) -> dict:
    times = []
    for _ in range(n):
        t = time.perf_counter()
        requests.get(url, timeout=30)
        times.append((time.perf_counter() - t) * 1000)
    times.sort()
    return {
        "P50": round(statistics.median(times), 1),
        "P95": round(times[max(int(n * 0.95) - 1, 0)], 1),
        "max": round(times[-1], 1),
    }
