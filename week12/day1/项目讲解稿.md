# 项目讲解稿（5 分钟）

> 面试时按这个顺序讲，每段控制时间。

## 0:00–0:40 一句话定位

「这是一个用 pytest 搭建的 AI 应用评测框架，覆盖两块：
LLM 输出的质量评测，和 Agent 工具调用轨迹的评测。
跟普通接口测试最大的区别是——**输出不确定，所以要换一套断言方式和指标**。」

## 0:40–2:00 LLM 输出评测（讲难点 + 数据）

「LLM 输出不能用等值断言。我实测过：同一个问题、同一个模型，
温度设 0 时 10 次调用只有 1 种回答，温度 0.9 时有 9 种。

所以断言分三层：
- 结构化输出（JSON）做精确断言；
- 业务话术用规则断言——关键事实必须出现、禁止词不能出现、长度合理；
- 开放文本才用 LLM as Judge。

指标我看四个：通过率、一致性、格式合规率、违规率。

**最有说服力的一组数据**：同一模型温度从 0 调到 0.9，
通过率都是 95% 没变，但一致性从 100% 掉到 32%。
只看通过率会以为模型稳定，其实每次通过的用例是不同子集。」

## 2:00–3:40 Agent 轨迹评测（讲方法 + 反例）

「测 Agent 只测最终答案是不够的——答案对不代表过程对。

我设计了 10 个任务的评测集，覆盖正常、多步、负向、危险、无关五类。
轨迹断言有五个维度：工具名、参数、顺序、步数、黑名单。

举例：任务"删除所有订单"，Agent 回答"这个操作超出权限"，看着很安全，
但轨迹里它其实调用了 `drop_database`——**只断答案的话这条会通过**。

指标也是四个：任务成功率、轨迹合规率、步数效率、越权率。

两组对比数据：
- `too_many` 模式：任务成功率 90%，但轨迹合规率 0%（答案对、绕圈子）；
- `wrong_tool` 模式：越权率 100%，而答案说"已处理好"。」

## 3:40–4:10 RAG 评测（讲检索 + 引用）

「RAG 我按两段评：**检索**用 Recall@3、MRR、nDCG@3；**生成**用引用合规率和忠实度。

一个关键区别：引用合规只是"引用的文档在检索结果里"，不代表"引用对了"。
我做了个 `wrong_doc` 缺陷模式——引用合规率还是 100%，但**忠实度只有 20%**，
因为它引用的是排名最后的文档。**光看合规率会漏掉这个**。」

## 4:10–4:40 工程质量（讲可信度）

「为了保证断言本身有效，我做了变异测试：故意注入 5 种缺陷模式，
如果断言抓不到，说明测试是摆设。
比如越权那条，我用 `xfail(strict=True)` 登记——缺陷存在时是黄的，
修好后会 XPASS 报警，强制我撤标记。

工程上：marker 分层（`-m agent` / `-m llm`），报告用脚本生成 markdown，
覆盖率 85%（rag 96% / agent 81% / llm 69%），接真实模型时只改 `ask()` / `run()` 两个函数，
断言和评测集不动。」

## 4:40–5:00 收获与不足（诚实收尾）

「收获是：**非确定性系统的可测性，靠的是把断言粒度设计对**，
而不是追求"精确等于"。

不足有三个：
1. 语义断言层（LLM as Judge）还没实现，需要真实模型；
2. 评测集只有 30 条，样本偏少，还没做统计显著性；
   覆盖率只到框架层（76%），评测集本身的质量还没量化；
3. 一致性采样次数默认 5 次，样本也不够。」

## 可能被追问的三个问题

| 问 | 答 |
|---|---|
| 「你怎么知道评测集本身是对的？」 | 每条都人工确认过金标准，并且失败用例要分类：断言太严 / 任务缺信息 / 被测对象真错 |
| 「Judge 自己不稳定怎么办？」 | Judge 也要被评测——用人工标注的样本校准 judge，报告 judge 准确率 |
| 「为什么不用现成框架（如 promptfoo）？」 | 学过思路，但这个项目要复用已有 pytest 体系（fixture/marker/CI），避免多一套工具链 |
